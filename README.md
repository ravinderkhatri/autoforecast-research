# AutoForecast

Compare forecasting models on the same data and save their predictions, scores and fitted models.
Use the included models or connect your own Python model.

For example, you might want to predict next week's sales for each product. AutoForecast checks
your data, tests models on earlier dates, and measures how well the chosen model predicts later dates.

![From input data to checked forecasts and saved results](assets/autoforecast-overview.svg)

## Start with a small example

You need **Python 3.12 or 3.13** and **Java 17**. Linux x86_64 and macOS Apple Silicon are supported.

```bash
git clone https://github.com/ravinderkhatri/autoforecast-research.git
cd autoforecast-research
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install .

export FORECAST_SPARK_CORES=2
export FORECAST_SPARK_MEMORY=1g

cd ..
autoforecast init-example my-experiment
autoforecast freeze --project-root my-experiment --source data
```

Set `JAVA_HOME` to your Java 17 installation if Spark cannot find Java.
Keep experiment folders outside the library checkout.

The example contains two products over 42 days: 84 observations, with no products excluded.
`freeze` checks the data and saves a **study**: a fixed copy of the data and evaluation rules.
Copy the printed `benchmark.json` path into:

```bash
autoforecast run --project-root my-experiment \
  --benchmark /absolute/path/printed/by/freeze/benchmark.json
```

This compares two simple models and prints the results folder. Each seven-day forecast has
14 values. Running the same command again resumes that campaign.
The example teaches the workflow; it does not establish which model is best for your data.

## Use your own data

Start from the example project. Your CSV or Parquet needs a series identifier, a date and a value:

| product | date | units |
|---|---|---|
| A | 2024-01-01 | 5 |
| A | 2024-01-02 | 0 |
| B | 2024-01-01 | 3 |

A **series** is one thing you forecast, such as a product or a product-store pair.
A **horizon** is how many future periods you predict: seven days for daily data, or seven months
for monthly data.

Before freezing, edit the files generated by `init-example`:

| File | What to change |
|---|---|
| `dataset.yaml` | Column names, frequency and season length |
| `recipe.json` | Series keys, training dates, forecast dates and scoring rules |
| `campaign.yaml` | Models and compute limits; keep its dates and selection metric consistent with the recipe |
| `models/*/model.yaml` | Settings for each model |

For a CSV, convert it first. Import preserves column names; it does not edit those settings.

```bash
autoforecast import-csv sales.csv my-experiment/custom-data/sales.parquet \
  --id-columns product --date-column date --target-column units
autoforecast freeze --project-root my-experiment --source custom-data/sales.parquet
```

Set `series_col: product`, `time_col: date`, `target_col: units` in the dataset and
`source_keys: ["product"]` in the recipe. Multiple source keys can identify a product-store pair.
Use matching frequencies in the dataset and recipe. For non-daily CSV files, also pass
`--frequency` to the import command. Supported frequencies include hourly, daily, weekly,
month-start/end and year-start/end; individual models may support fewer.

Observed values must be finite and nonnegative. A missing observation is not automatically zero.
Choose the missing-data rules explicitly. Changing the data or study rules creates a new study ID.

## Use AutoForecast from Python

Use this route when your application already owns the data and model code.
Register the data once, then run models using the returned study ID.

<details>
<summary>A small study.yaml for daily data</summary>

This example expects `input.parquet` with columns `product`, `date` and `units`, covering
1 January through 11 February 2024. Dates in YAML must be quoted. File paths are relative
to this configuration file.

```yaml
schema_version: 1
dataset:
  schema_version: 1
  dataset:
    id: example
    panel:
      series_col: product
      time_col: date
      target_col: units
      frequency: D
      season_length: 7
      target_estimand: observed_nonnegative
recipe:
  schema_version: 2
  source_keys: [product]
  frequency: D
  training_start: "2024-01-01"
  validation_origins: ["2024-01-28"]
  validation_horizon: 7
  final_train_cutoff: "2024-02-04"
  final_test_horizon: 7
  history_policy: fixed
  new_series_policy: error
  target_unit: units
  feature_availability: {}
  metric: mae
  history_missing: preserve
  actual_missing: error
source:
  kind: parquet
  path: input.parquet
storage:
  root: saved-studies
```

</details>

For a local session:

```python
from pyspark.sql import SparkSession
from autoforecast import register_study, run_study
from autoforecast.study_registration import StudyRegistry

spark = SparkSession.builder.master("local[2]").getOrCreate()
registry = StudyRegistry.from_config("study.yaml", spark=spark)
study_id = register_study("study.yaml", registry=registry)
result = run_study(study_id, "seasonal_naive", registry=registry)
print(result.summary())
```

If your environment already supplies `spark`, use that session. Registration checks and saves
the data; it does not train a model. `seasonal_naive` is the built-in model supported by this
convenience call. Connect other models with the callback below.

## Connect your own model

Your function trains a model, writes its predictions and saves its fitted model files.
AutoForecast supplies the training history, forecast dates, parameters and random seed.
It then checks and scores the returned predictions.

Tell AutoForecast where your model code lives by adding this to `study.yaml`:

```yaml
runtime:
  implementation:
    source_roots:
      model: models
```

Reload the registry after editing the config. You do not need to register unchanged data again.
Use one more named root, such as `shared: shared_code`, if helpers live in another folder.

<details>
<summary>A complete constant-value model for learning</summary>

This small example predicts the same number for every product and date.
Save it as `models/constant.py`. It is an integration example, not a production model.

```python
import json
import pyarrow as pa
import pyarrow.parquet as pq
from autoforecast.panel import Forecast
from autoforecast.study_tuning import FitPredictResult


def fit_predict(request):
    level = request.model_parameters["level"]
    products = [row[request.panel.series_col] for row in request.series_mapping.collect()]
    folder = request.output_dir / "forecasts"
    folder.mkdir()
    rows = [
        {"series_id": product, "date": day, "yhat": level}
        for product in products for day in request.forecast_dates
    ]
    pq.write_table(pa.Table.from_pylist(rows), folder / "part.parquet")

    model_folder = request.output_dir / "model"
    model_folder.mkdir()
    (model_folder / "parameters.json").write_text(json.dumps({"level": level}))
    forecast = Forecast(
        adapter=request.model_id, path=str(folder), origin=request.origin,
        horizon=len(request.forecast_dates), n_series=len(products),
        disposition={"emitted": len(rows)}, frequency=request.panel.frequency,
        target_estimand=request.panel.target_estimand,
    )
    return FitPredictResult(forecast, "constant-json-v1")
```

Save its settings as `model.yaml` beside `study.yaml`:

```yaml
schema_version: 2
model: {id: constant-example, adapter: external}
hyperparameters:
  model.level:
    default: 4.0
    valid: {kind: float, low: -10.0, high: 100.0, log: false}
    search: {kind: float, low: 1.0, high: 10.0, log: false}
```

`valid` sets the allowed values. `search` sets the range used only when tuning is enabled.
Replace the constant calculation with your own training and prediction code, and use
`request.seed` when your model uses randomness.

</details>

Run it from the folder containing `study.yaml` and `models/`:

```python
from models.constant import fit_predict

registry = StudyRegistry.from_config("study.yaml", spark=spark)
result = run_study(
    study_id, fit_predict, registry=registry, model_config="model.yaml",
    fixed_parameters={}, tracking="none", publish=False,
)
print(result.validation_metrics)
print(result.testing_metrics)
print(result.path)
```

`fixed_parameters={}` uses the defaults without searching. A successful run fits twice:
once for validation and once on the later training data for the final test.
The callback's output folder is temporary. Keep `result.path`, which points to the saved run.
Predict every supplied series/date pair. Model files belong in `output_dir / "model"`;
optional logs or feature importance belong in `output_dir / "artifacts"`.

AutoForecast saves the selected model source and checks it before and after each fit.
Editing a helper changes the model's source identity, not the data-study ID.
Saved files cannot prove which cells a notebook executed or which hidden state a function used.
Include all relevant helpers and keep model settings in the profile.

**Predictions are kept as supplied, including negative values.** AutoForecast does not clip them
or offer a replacement switch. For actuals `[0, 1, 2]` and predictions `[-2, 1, 3]`, MAE is `1`.
NaN, infinity, missing or duplicate forecast cells and changed saved files still fail validation.
If you need nonnegative predictions, make that part of your model or its own wrapper and record
that code. Already have forecasts? Use `Study.evaluate_forecasts` to score saved predictions.

## Choose model settings

**Tuning** tries different settings. **Cross-validation** tests them on several earlier time
windows. **Refitting** trains again using the chosen settings and more recent history.
The final test is kept separate from choosing settings.

Inside the existing `recipe:` section of `study.yaml`, add `tuning_windows` below.
Keep the other recipe settings:

```yaml
tuning_windows:
  - {origin: "2024-01-14", horizon: 7}
  - {origin: "2024-01-21", horizon: 7}
```

Add these sections to `model.yaml`:

```yaml
hpo: {backend: optuna, max_trials: 5, seed: 42}
selection: {stage: tuning, origins: all, metric: mae}
```

The study rules changed, so reload the registry and register again. Use the new study ID
and omit `fixed_parameters` to enable tuning:

```python
registry = StudyRegistry.from_config("study.yaml", spark=spark)
study_id = register_study("study.yaml", registry=registry)
result = run_study(
    study_id, fit_predict, registry=registry, model_config="model.yaml",
    tracking="none", publish=False,
)
```

Five settings across two windows means ten tuning fits, followed by validation and refit:
12 fits in total. Without an `hpo` section, `run_study` uses fixed settings.
MAE is the average size of the errors; lower is better. Other supported scores include
RMSE, WAPE and WRMSSE. WRMSSE also needs weights and scales.

## Open the results

Start with `result.summary()` and the generated `RUN.md` inside `result.path`.
The run folder contains forecasts, scores, model files and the settings used.
Check missing-data coverage before comparing scores. An unavailable score is `None`, not zero.

```python
from autoforecast.study_workflow import load_forecast_workflow
from autoforecast.results import read_workflow_results, export_results

saved = load_forecast_workflow(result.path)
print(saved.validation_metrics)
tables = read_workflow_results(result.path, include_tuning=True)
export_results(tables, result.path.parent / (result.path.name + "-analysis"))
```

Loading checks the saved files without retraining. Keep the referenced study and tuning folders
too; a workflow folder may not contain every input. Each ordinary workflow call creates a new run.
Campaigns can resume matching saved work.

<details>
<summary>Source records, reuse and notebook limits</summary>

Roots are resolved relative to the original registry config. The default file types are
Python, YAML, JSON, TOML, INI, CFG and SQL. Optional `include` and `exclude` lists use
root-relative glob patterns; `*` matches nested paths. Includes replace the default type list.
Common VCS, cache, environment, build, data and output folders are excluded. Filename exclusions
match `.env*`, `*credentials*`, `*secret*`, `*.pem`, `*.key`, `*.p12` and `*.pfx`, ignoring case.
These patterns cannot detect other credential names or secrets inside source code.
Keep run outputs outside the selected source, or exclude their folders.

Missing, empty or overlapping roots, unreadable selected files and selected symlinks fail.
An importable Python function's defining file must be selected; this also applies to bound
methods, callable instances and partial functions with Python source. For a class constructor,
use a saved function wrapper or an explicit `implementation=` identity. Callables without
available Python source have no defining-file check. A saved notebook export can be included with `*.ipynb`,
but retaining it does not prove it was executed. AutoForecast does not trace dynamic imports
or save closure values, partial arguments or object state. Put settings in the model config and parameters.
Saved files do not prove which code was executed. Model code is trusted Python;
AutoForecast cannot control other data it reads.

Source files and metadata are saved in `metadata/implementation/` and checked when loaded.
The callback location, logical file paths and file contents identify the implementation.
Moving unchanged folders preserves that identity.
Python/package versions and the library revision are recorded separately; installed packages
are not proof of imports. Reload uses the saved copy, while further fitting checks current source.

An explicit `implementation=` dictionary with `name`, `version`, `source_sha256` and `dependencies`
still works and takes precedence over automatic capture. It is caller-declared evidence.
To fit saved settings on a new study, use `study.run_forecast_workflow` with
`selected_config=result.selected_config`, the same implementation identity and no new fixed settings.
Use a registered Study loaded through `registry.load_study` to carry the configured source roots.

</details>

<details>
<summary>Several models or machines</summary>

Use `study.run_campaign(models=[...])` with a `StudyModel` for each importable callback:
`StudyModel("models.constant:fit_predict", config="model.yaml", fixed_parameters={})`.
Import `StudyModel` from `autoforecast.study_campaign`.

The default runs models in sequence. `execution="local", max_parallel_models=2` runs up to two
model jobs on one machine. `execution="cluster", ray_address="..."` uses an existing Ray cluster.
Available resources may reduce concurrency. Trials and windows within each model stay sequential.
AutoForecast does not distribute an arbitrary model's internal training algorithm.

Workers need matching code and accessible study/output paths on shared local or mounted storage.
Object-store URLs are unsupported. Use `AUTOFORECAST_SOURCE_ROOTS` with a JSON mapping of logical
root names to worker-local folders when paths differ. Workers check the saved source baseline
before fitting or reuse; the mapping does not deploy code. Real two-machine testing remains pending.
Use `final_evaluation="validation_winner"` to refit only the winner or `"all_models"` for all models.
Python campaigns save a workflow per model and phase; inspect both validation and final phases.

![One machine, several processes, and several machines](assets/03-parallel-execution.svg)

</details>

<details>
<summary>Data preparation, missing observations and WRMSSE</summary>

Choose the population and dates before registration. Each series starts at its first available
observation, or at an explicitly configured start; the library does not invent earlier history.
`history_missing: zero` fills gaps in fitting data. For evaluation, `actual_missing: error`
refuses gaps, `mask` leaves them out of the score, and `zero` counts them as zero. Missing and
filled counts remain visible. Raw actuals are preserved.

Use `register_study(..., prepare=your_preparation)` when your application owns eligibility or
transformation rules. The hook validates settings and returns prepared data, retained/excluded
keys and reasons. AutoForecast checks that the counts and actual keys agree, then saves those
decisions. See the [preparation contract](autoforecast/study_registration.py) and
[preparation helpers](autoforecast/preparation.py). Configuration never imports the hook for you.

WRMSSE needs a weight and a positive scale for each required series/window. Supply references
or configure the daily reference calculator. `check_wrmsse_references` reports invalid weights,
scales and totals without changing data. Registration defaults to rejecting invalid references;
`invalid_references: exclude` explicitly removes affected series across all windows.
See [reference calculation and checks](autoforecast/study_references.py).

</details>

<details>
<summary>MLflow and Delta</summary>

The default is `tracking="none", publish=False`: results stay in the configured file storage.
`tracking="mlflow"` exports checked results to an existing experiment; provide `tracking_uri`
and `mlflow_experiment`. It does not create an experiment.
`publish=True` writes to the configured Delta registry. The two controls are independent.
Explicit arguments override environment settings, which override registry runtime settings.

Delta requires a compatible Delta-enabled Spark session and credentials supplied by your runtime.
Set `storage.namespace` to the destination namespace. Registration manages the shared study,
observation, issue, result and forecast tables. Runs and reads do not provision tables.
Delta sources use read-only SQL over declared table aliases; table versions and source queries
are recorded. Audit queries can supply a separate starting population for a preparation hook.
Shared artifact storage still needs POSIX file and lock support; Delta is not a replacement for it.
File and table publication is not one transaction, and old table versions may expire after vacuum.

Failed result publication leaves the completed workflow available. Reload it and retry
`registry.publish_results(saved.study_id, saved.path)`; no refitting is needed.
See [tracking exports](autoforecast/run_mlflow.py) and [Delta integration](autoforecast/integrations/delta.py).

</details>

## Development

Tests live beside the code. Install the `ci` dependency group and the model extras your tests need,
then run `python scripts/run_tests.py`. Each test module runs in a separate process.

CI checks linting, types, regressions, installed wheels and model extras. Ten regression shards
use saved timings to balance the work without dropping tests. New or changed timing estimates belong
in `configs/ci/test_durations.json`. Local Linux containers can run the same test entry points;
ARM containers on Apple Silicon do not replace the Linux x86_64 checks.
